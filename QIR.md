# HURCULES — QIR Quantum Strategy Map

> QIR = Quantum-Inspired Reasoning. Three strategies, applied ONLY where they add
> value — never ceremony. Each entry names the stage, the strategy, and the concrete
> mechanism. If a stage has no entry, QIR is NOT applied there (deterministic code
> must stay deterministic).

## The Three Strategies (recap)

1. **SUPERPOSITION** — generate multiple candidate approaches/interpretations before
   committing to one. Used when the space of answers is large and the cost of
   exploring in parallel is low.
2. **ENTANGLEMENT** — map ripple effects BEFORE changing anything. Every decision
   lists its blast radius: what else depends on it, what breaks, what must change
   in lockstep.
3. **ANNEALING** — escape the obvious-but-mediocre answer. After a candidate solution
   looks "good enough," deliberately attack it: find the failure mode, the simpler
   design, the cheaper path. Settle only after the answer survives its own critique.

## WHERE QIR APPLIES

### STAGE 0 — Product Contract
- **Superposition (contract options):** draft 2-3 alternative output-package shapes
  and scoring rubrics before locking GOAL.md. Choose by fit, not habit.
- **Entanglement (contract blast radius):** before freezing the 7-part output,
  map what each part commits downstream (schema, registry, Hermes adapter).
  A contract change after Stage 4 is a migration — cost it now.

### STAGE 1 — Gold-Standard Set
- **Superposition (repo selection):** candidate repo list generated by 3 independent
  lenses (utility, risk, variety), merged and deduped. Missing a category is a
  coverage bug.
- **Annealing (gold labels):** after labeling a repo, have a second agent attack the
  labels — "which capability here is NOT actually implemented?" — before the
  gold file is accepted.

### STAGE 2 — Deterministic Mapper
- **NO QIR.** This stage must be deterministic and reproducible. Quantum strategies
  would introduce variance. (Entanglement applies to the OUTPUT SCHEMA though: schema
  change ripples into analyst, compiler, registry — pin it early.)

### STAGE 3 — Capability Analyst
- **Superposition (multi-model analysis):** run the analysis with ≥2 different models
  (e.g., deepseek-v4-flash-free + nemotron-3-super:free via OmniRoute) on the same
  mapper output; diff the capability candidates. Divergence = uncertainty to surface,
  not to hide.
- **Annealing (adversarial pass):** a dedicated "devil's advocate" agent tries to
  break each claimed capability: "does this really exist in the code, or is the
  README lying?" Only capabilities that survive land in the output with confidence ≥
  threshold.
- **Superposition (claim separation):** the 4-way split (claims/demonstrates/verifies/
  uncertain) is itself a superposition of interpretations — keep them separate,
  never collapse into one confident narrative.

### STAGE 4 — Capability Compiler
- **NO QIR in validation logic.** The compiler's job is deterministic rejection of
  invalid packages. Quantum reasoning must not soften the gates.
- **Entanglement (schema ripple):** any schema change lists all consumers
  (validator, registry, Hermes adapter, gold files) in the PR description. No
  schema edit without the entanglement map.

### STAGE 5 — Evaluation Gates
- **Superposition (test generation):** generate failure-case tests from multiple
  attack angles (input fuzzing, injection, resource abuse, fabricated citations) —
  not just the happy-path tests.
- **Annealing (rubric attack):** before accepting a "PASS," an adversarial pass asks
  "how could this evaluation be fooled?" — if the eval can be gamed, fix the eval.

### STAGE 6 — Hermes Integration
- **Entanglement (spawn ripple):** before adding any registry/adaptor field, map what
  depends on it (sub-agent construction, permissions, provenance display). A new
  field with no consumer is dead weight (YAGNI).
- **Superposition (sub-agent assembly):** generate 2-3 candidate capability
  compositions for a task; pick the minimal one that meets the task contract.
  Composition = superposition over capability subsets.

### STAGE 7 — Sandboxed Execution
- **Annealing (sandbox attack):** a red-team agent deliberately tries to escape the
  sandbox (path traversal, env leak, socket access, fork bombs) — every successful
  escape is a blocker, not a note.
- **Entanglement (permission ripple):** every new capability permission maps to its
  sandbox capability; no permission without a sandbox counterpart.

### STAGE 8 — Discovery
- **Superposition (ranking lenses):** candidate repos ranked by ≥2 independent
  scorers (relevance, risk, novelty); disagreement = review flag, not tiebreak.

### STAGE 9 — Composition & Spawning
- **Entanglement (agent graph):** every composed agent ships with its dependency
  graph (which capabilities, which commits, which handoffs). Breaking one node
  must visibly ripple through the map BEFORE it happens in production.
- **Superposition (composition candidates):** 3 candidate assemblies per task,
  evaluated, best wins. Never the first assembly that type-checks.

### STAGE 10 — Productisation
- **Entanglement (product ripple):** any monetisation/policy change maps affected
  surfaces (accounts, registry, marketplace, adapters) before implementation.
- **Annealing (product critique):** before shipping a feature, an adversarial review
  asks "does this advance the moat (repo→capability dataset) or just the demo?"

---

## QIR GUARDRAILS

- **Determinism wins.** Any stage marked "NO QIR" is a hard exclusion — do not
  quantum-ify deterministic code.
- **Cost-aware.** Superposition is bounded (max 3 candidates, max 2-3 models) —
  zero-cost free models preferred; never pay per candidate.
- **Survivable outputs.** Annealing may kill an idea; that's a WIN (cheap failure),
  not a loss. Record what was rejected and why in the issue/ADR.
- **QIR is a means.** If a strategy adds ceremony without catching errors or
  improving decisions, drop it from that stage.
